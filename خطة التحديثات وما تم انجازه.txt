
الوضع الحالي
لن أبدأ أي تعديل الآن. هذه خطة الإصلاح والتطوير المقترحة أولاً، مبنية على التحليل الكامل للمشروع، وبنفس الشروط التي ذكرتها: تعديل جراحي، عدم كسر أي منطق سليم، ومراعاة تكامل الصفحات والـ flows بالكامل.

1) المشاكل المكتشفة

يوجد Schema Drift بين الكود وقاعدة البيانات الموثقة داخل المشروع. الكود يعتمد على عناصر غير موثقة بالكامل داخل migrations الحالية مثل create_order_atomic وarchived_at وadmin_audit_logs وبعض أعمدة مثل low_stock_threshold.
توجد أسرار تشغيل حساسة داخل .env.local ويجب اعتبارها نقطة خطر عالية.
منطق التسجيل register غير سليم معمارياً وأمنياً بسبب الاعتماد على منطق Admin-like من جهة العميل.
مسارات الإدارة فيها حماية جيدة مبدئياً، لكن توجد لا-اتساقات بين middleware وvalidateAdminSession وforce-logout وإبطال الجلسات.
حالة الطلب لها أكثر من مصدر حقيقة: orders.status وorder_tracking_events.
عناصر الطلب لها تمثيل مزدوج: items_snapshot وorder_items بدون حوكمة واضحة لمصدر الحقيقة.
منطق السلة موزع بين CartContext وAPI routes وcartService، ما يزيد احتمالات التضارب مع الوقت.
الاعتماد كبير على client-side fetching في صفحات مهمة، وهذا يضعف الأداء ويزيد الـ waterfall.
يوجد استخدام واسع لـ <img> بدل next/image في نقاط مؤثرة على الأداء.
لا توجد طبقة اختبارات فعلية unit/integration/e2e.
مجلد public متضخم جداً وفيه أصول كثيرة ومكررة ونسخ احتياطية.
بعض ملفات الواجهة قديمة أو placeholder وتزيد التشويش المعرفي.
analytics الحالية جيدة كبداية لكن ما زالت تعتمد على قراءة تشغيلية مباشرة أكثر من اللازم.
PDF generation يتم وقت الطلب، وهذا قد يصبح bottleneck لاحقاً.
لا توجد حدود Domain صارمة بين catalog/cart/orders/promos/admin.
2) ترتيب المشاكل حسب الأولوية

توحيد حقيقة قاعدة البيانات وإغلاق فجوة Schema Drift.
تأمين الأسرار والجلسات الإدارية ومسارات العمليات الحساسة.
إصلاح منطق التسجيل والمصادقة غير الناضج.
توحيد منطق الطلبات ومصدر الحقيقة لحالة الطلب والعناصر.
حماية تكامل السلة والـ checkout والطلب من أي تضارب داخلي.
تقليل المخاطر التشغيلية في الإدارة والأرشفة والحذف والاستعادة.
تحسين الأداء في الصور والتحميل والصفحات الأكثر زيارة.
بناء طبقة اختبارات تمنع regressions قبل أي تطوير أكبر.
تنظيف الأصول والملفات غير الضرورية.
بدء تحسينات التطوير والـ scaling.
3) خطة الإصلاح المحكمة
المرحلة 1: Stabilization حرجة

جرد كل ما يعتمد عليه الكود في Supabase ومقارنته مع migrations وDatabase Schema.
توثيق العناصر المفقودة وإضافة migrations جراحية فقط بدون تغيير سلوك قائم.
تأكيد وجود create_order_atomic وarchived_at وadmin_audit_logs وبقية الاعتمادات قبل لمس أي منطق.
تجميد أي refactor كبير إلى أن تصبح صورة الـ DB مكتملة.
المرحلة 2: Security Hardening

تدوير الأسرار الحساسة ونقلها إلى إدارة أسرار سليمة.
توحيد التحقق الإداري بين middleware وvalidateAdminSession.
مراجعة force-logout وآلية invalidation حتى تكون متسقة فعلاً.
قفل endpoints الحساسة مثل reset/archive/hard-delete بمستوى أعلى من الضبط والتحقق.
المرحلة 3: Auth & Account Fixes

إزالة أي منطق Admin-like من client-side registration.
جعل التسجيل وتحقق وجود المستخدم يتمان عبر backend آمن فقط.
مراجعة login/register/callback/sync للتأكد من عدم كسر checkout redirect وOAuth flow.
المرحلة 4: Order Integrity

تحديد مصدر الحقيقة الرسمي لحالة الطلب.
تحديد دور items_snapshot مقابل order_items.
تثبيت contract واضح لمسار إنشاء الطلب.
مراجعة flows: review -> POST /api/orders -> confirm -> orders -> admin tracking.
أي تعديل هنا سيكون جراحياً مع اختبارات flow قبل وبعد.
المرحلة 5: Cart Integrity

تقليل التكرار بين CartContext وAPI وservice layer.
تثبيت merge logic وسلوك stock validation.
التحقق من أن guest cart وauth cart لا يفقدان بيانات ولا يكرران عناصر.
المرحلة 6: Admin Reliability

مراجعة delete/archive/restore/hard-delete.
التأكد أن أي عملية إدارة لا تكسر analytics أو tracking أو inventory.
إضافة safeguards خفيفة قبل التنفيذ الجماعي bulk actions.
المرحلة 7: Performance

استبدال الصور الحرجة إلى next/image بشكل جراحي.
تخفيف client fetching في الصفحات الأعلى تأثيراً.
إضافة pagination حيث يلزم.
تنظيف public من النسخ المكررة والاحتياطية غير المستخدمة.
مراجعة caching strategy للمنتجات والأقسام والعروض.
المرحلة 8: Testing Guardrail

unit tests للمساعدات والمنطق الخالص.
integration tests لمسارات API الحرجة.
e2e flows للسلة والطلب والإدارة.
أي إصلاح لاحق لن يدخل قبل وجود guard مناسب في الجزء المتأثر.
4) خطة التطوير والتحسين

بناء Search حقيقي للمنتجات.
فصل inventory logic عن product catalog تدريجياً.
إضافة notification layer محترمة بدل الاعتماد الحالي المحدود.
ترقية promos إلى campaign model أنضج.
تحسين analytics بمصدر read optimized.
تحسين admin UX للأوامر الجماعية والفلاتر والوضوح التشغيلي.
تجهيز المنصة لمرحلة scaling عبر فصل domains وليس عبر refactor شكلي.
إدخال audit logging حقيقي للعمليات الإدارية.
تحسين invoice pipeline إذا زاد الحجم.
تأسيس roadmap لفصل الخدمات لاحقاً عند الحاجة، لا قبلها.
5) قواعد التنفيذ التي سألتزم بها أثناء الإصلاح

أي تعديل سيكون صغيراً ومحدود النطاق.
قبل تعديل أي جزء سأراجع تأثيره على الصفحات والـ API المرتبطة به.
لن ألمس أي منطق سليم لا يخدم المشكلة الحالية.
سأعمل على مراحل قصيرة مع تحقق بعد كل مرحلة.
سأبدأ دائماً بالأجزاء الأعلى خطراً والأقل قابلية للمسامحة.
أي جزء يمس auth/cart/orders/admin سأتعامل معه كمنطقة حساسة عالية الترابط.
6) خطة البدء المقترحة

Phase A: Schema + Security Stabilization
Phase B: Auth + Orders Integrity
Phase C: Cart + Admin Reliability
Phase D: Performance + Cleanup
Phase E: Testing + Safe Enhancements
